# ADR-001: Справочно-ориентированная архитектура объектов

Статус: принято
Дата: 2026-08-30

## Контекст

GIS-сервис должен работать с объектами инфраструктуры провайдера: столбы, линии оптики, трассы, дома абонентов, активное сетевое оборудование и т.д. Набор объектов может расти без изменения кода.

Требования:
- переключаемое отображение объектов по слоям;
- разграничение прав на отображение и изменение на уровне типов объектов;
- единый код CRUD, тайлов и прав без хардкода типов.

## Решение

Не создавать по таблице на каждый тип объекта. Ввести справочник типов объектов (`object_types`) и единую таблицу объектов (`objects`).

- Справочник `object_types` описывает каждый тип: имя, геометрию, слой, стиль отображения, схему атрибутов (`attrs_schema`, JSON Schema).
- Атрибуты объектов хранятся в JSONB и валидируются в `api` по `attrs_schema`.
- Слои (`layers`) — отдельный справочник для группировки типов и управления видимостью.
- Связи между объектами — через справочник типов связей (`relation_types`) и таблицу `object_relations`.
- Права доступа динамические: `objects:<code>:read|write`, `object-relations:<code>:read|write`, `object-types:manage`.

## Следствия

Положительные:
- добавление нового типа объекта не требует изменений в коде `api`, `tiles`, web — достаточно записи в справочнике;
- права и слои строятся из справочника автоматически;
- один generic-CRUD вместо N эндпоинтов.

Отрицательные / риски:
- атрибуты в JSONB менее типизированы, качество данных держится на валидации по JSON Schema;
- сложнее построение выборок/отчётов по конкретным атрибутам;
- админ-интерфейс для ведения справочника обязателен (решение: реализовать в web).

## Управление справочником

Справочники ведутся через админ-интерфейс в web (`object-types:manage`). Первичный набор типов закладывается миграциями/seed как исходные данные.
